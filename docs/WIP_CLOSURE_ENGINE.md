# Little's Law WIP Closure Engine

`anti-llm-cheat-lsp` treats unfinished work as an admissibility problem.

The WIP engine consumes two bounded observation surfaces:

1. the checked-out source tree, scanned read-only for explicit unfinished-work evidence; and
2. an admitted GitHub activity snapshot using `chatman.wip.github-snapshot/v1`.

It produces a typed WIP object graph, observed Little's Law metrics, a ranked reversible closure frontier, and an OCEL 2.0 projection. It **never actuates** a GitHub mutation. Every closure candidate is `INTENT_ONLY` and `receipt_required=true`.

## Law

For an admitted observation window, Little's Law is used as the governing flow relation:

\[
L = \lambda W
\]

The scanner does not assume a finite sample is automatically in steady state. It reports observed `L`, observed closure throughput, observed completed cycle time, and `L/lambda` separately so departures are visible rather than laundered into an equality claim.

- `L`: logical unfinished-work objects after collapsing linked issue/PR/CI/branch evidence.
- `lambda`: observed closed/merged/published objects per day.
- `W`: observed mean cycle time for completed objects.
- `L/lambda`: projected WIP residence time when throughput is observed and non-zero.

Absence of WIP findings does not manufacture `ALIVE`; the report remains `UNKNOWN` without execution evidence.

## Process

```text
source + GitHub activity snapshot
        |
        v
admit/refuse snapshot schema
        |
        v
collapse GitHub/source evidence into WIP objects
        |
        v
compute L, lambda, W
        |
        v
construct maximal reversible closure candidates
        |
        v
rank closure frontier by transitive WIP reduction / estimated closure cost
        |
        v
INTENT_ONLY
        |
        +---- external bounded executor / BRCE ----> receipt
```

The scanner is intentionally on the observation/CONSTRUCT side of the authority boundary. It does not call GitHub, merge pull requests, push commits, rerun workflows, close issues, or publish releases.

## CLI

The `wip` noun exposes four read-only capability surfaces:

```bash
cargo run -- wip languages
cargo run -- wip source --dir .
cargo run -- wip scan --dir . --snapshot examples/wip-snapshot.json
cargo run -- wip frontier --dir . --snapshot examples/wip-snapshot.json
cargo run -- wip scan --dir . --snapshot examples/wip-snapshot.json --json
cargo run -- wip scan --dir . --snapshot examples/wip-snapshot.json --ocel
```

`wip languages --json` exposes the admitted Tree-sitter grammar registry for machine consumers. The exact argument spelling is generated by `clap-noun-verb`; the Rust verbs remain the source of truth.

## Polyglot Tree-sitter source admission

Programming-language source is **AST-first**. A file with an admitted Tree-sitter grammar is parsed before unfinished-work classification; the generic line scanner is not run over that file. This prevents marker-like strings such as `"TODO"` from becoming WIP merely because the token exists in source text.

The admitted grammar registry currently covers:

- Rust;
- TypeScript and TSX;
- JavaScript and JSX;
- Python;
- Go;
- Java;
- C;
- C++;
- C#;
- Bash.

The scanner admits syntax-specific unfinished work rather than pretending languages share one syntax. Examples include Rust `todo!` / `unimplemented!`, Python pass-only or ellipsis-only function bodies and `NotImplementedError`, Go unfinished `panic` calls, Java/C# not-implemented throws, JavaScript/TypeScript unfinished throws, and C/C++ unfinished `#error` directives. TODO/FIXME/XXX/HACK/TBD comments remain visible because they are admitted from comment AST nodes, not arbitrary text.

Tree-sitter error or missing nodes are classified as `BUILD_BROKEN`. Failure to load or execute an admitted parser is surfaced as `UNSUPPORTED`, not silently converted into a clean scan. Ambiguous `.h` files are parsed as both C and C++; the lower-error syntax tree is selected deterministically. Test/spec paths are typed as `TEST` WIP instead of generic `CODE` WIP.

## Snapshot schema

| Field | Meaning |
| --- | --- |
| `schema_version` | Must be `chatman.wip.github-snapshot/v1`; other schemas are refused. |
| `observed_at` | RFC 3339 observation boundary used for all age/window calculations. |
| `window_days` | Observation window for throughput and completed cycle times. |
| `workspace_repository` | Optional repo identity for the checked-out source tree. Required to attribute source WIP when the snapshot contains multiple repositories. |
| `repositories` | GitHub repository observations. |

Each repository can contain branches, pull requests, issues, workflow runs, releases, commits, and dependency edges. Commit timestamps are a fallback for branch/PR activity. `dependency_edges[].to` is the blocked prerequisite; `from` is the dependent. Either endpoint may be a logical WIP id such as `github:owner/repo/pr/42` or a repository identity such as `owner/repo`.

## Logical WIP collapse

The unit counted in `L` is not a GitHub API object. The engine collapses observable projections where identity is admitted:

```text
issue #3
  -> PR #10
      -> feature branch
          -> failed workflow

= one logical PR/CI WIP object
```

An open PR suppresses its branch as a separate WIP object. A failed workflow associated with that open PR is folded into the PR. An issue explicitly linked to that open PR is also folded into the PR. Unlinked issues, orphan branches, standalone workflow failures, draft releases, and source WIP remain separate logical objects.

Source findings are collapsed by `(path, WIP kind)` so a file containing five unfinished markers is not automatically counted as five independent flow units.

## WIP taxonomy

The engine models `CODE`, `TEST`, `INTEGRATION`, `DEPENDENCY`, `CI`, `REVIEW`, `MERGE`, `RELEASE`, `DOCUMENTATION`, `EVIDENCE`, `RECEIPT`, `REPLAY`, `GENERATED_PROJECTION`, `ORPHAN_BRANCH`, `STALE_PR`, `ABANDONED_EXPERIMENT`, `DUPLICATE_IMPLEMENTATION`, `UNSATISFIED_REQUIREMENT`, `CROSS_REPO_BLOCKER`, and `SOURCE_MARKER`.

Standing uses `UNKNOWN`, `PARTIAL_ALIVE`, `ALIVE`, `BLOCKED`, `BUILD_BROKEN`, `UNSUPPORTED`, and `REFUSED`. `UNKNOWN != ALIVE`; a clean scan is not a successful execution receipt.

## Source fallback admission

For prose, configuration, and extensions without an admitted grammar, the bounded text fallback recognizes explicit unfinished implementation evidence:

- `TODO`, `FIXME`;
- Rust-like `todo!(` and `unimplemented!(` where no grammar owns the file;
- `stub implementation` / `not implemented`;
- machine-local `file:///` replay pointers;
- declared status/standing lines such as `Status: BLOCKED` or `Standing: PARTIAL_ALIVE`;
- missing Cargo path dependencies.

Generic prose that merely lists status vocabulary is not admitted as WIP. Generated projections, receipts, transcripts, OCEL output, vendored dependencies, `target`, and VCS internals are excluded from source WIP admission.

## Closure frontier

For each admitted WIP object, the engine preserves multiple reversible lawful closure candidates when more than one path exists. Candidate actions include repairing exact-head CI, finishing implementation, resolving/materializing blockers, adding evidence or receipts, replacing non-replayable evidence pointers, requesting review, merging verified merge-ready work, releasing through a bounded path, opening a PR for unmerged work, comparing/superseding stale work, and closing an issue only after observed satisfaction.

Priority is computed from:

```text
(expected WIP reduction
 + 2 * blocked dependents
 + 0.05 * age_days
 + standing urgency)
 / estimated closure cost
```

This is a ranking heuristic, not actuation authority. All frontier entries carry `authority = INTENT_ONLY` and `receipt_required = true`.

## OCEL projection

`--ocel` emits an OCEL 2.0-shaped projection containing repository/WIP objects, `WipObserved` events, and `ClosureIntentConstructed` events. The projection records that intents were constructed; it does not fabricate execution events.

## Evidence and replay

For deterministic replay, retain the exact snapshot JSON together with the scanned source SHA/tree identity, scanner source identity, report JSON or OCEL projection, and subsequent executor receipts if any closure intents are actuated.

A future executor may consume closure intents, but it must independently admit authority and emit a receipt for every DO transition.
